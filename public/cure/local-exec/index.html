Run commands on your own machine

← Back to the app

When research needs a shell — running a script, checking a file, testing a snippet — DeepResearch boots a Linux VM inside your browser. That is private by construction, but it is an emulator: slow to start, slow to run, fixed to one disk image, and sealed off from the computer you are actually sitting at.

The local runner is the alternative. It is a small service you start on your own machine; DeepResearch calls it straight from the browser and every research session gets its own throwaway container — created on the first command, destroyed when you are done. Native speed, any image you like, and your own tools.

Where your commands go. Browser → localhost → a container on your machine. Nothing is sent to deepresearch.se; the site's server is not in this path at all. On the Se/cure tier the runner's address and key live only inside your sealed session in this browser.

Quick start

You need two things: a container runtime (one of the choices below) and Node 18+ (brew install node on a Mac). Then one line:

curl -fsSL https://deepresearch.se/cure/local-exec/runner.mjs -o runner.mjs && node runner.mjs

It finds whichever runtime you have installed, pulls a small Debian image once, and prints the address to paste back. Then, in Settings → Execution environment:

  1. Environment: Local runner — your machine
  2. Runner URL: http://localhost:8100
  3. Press Test connection — it should report the runtime it found.
  4. Turn the execution sandbox on and ask something that needs a shell.

Prefer not to leave a file behind? Pipe it:

curl -fsSL https://deepresearch.se/cure/local-exec/runner.mjs | node --input-type=module

Pick a container runtime — macOS

Apple's built-in container — nothing to install

macOS 26 and later ship a native container command that gives each container its own lightweight VM. If you have it, the runner picks it up on its own and there is no step here at all. Check with:

container --version

Podman — rootless, daemonless, one brew

The lightest thing to install on an older Mac:

brew install podman && podman machine init && podman machine start

Docker

Docker Desktop, or the leaner CLI-only route through colima:

brew install docker colima && colima start

Docker Desktop and OrbStack both work as-is — brew install --cask docker or brew install --cask orbstack.

Linux

Podman is rootless and usually already packaged:

sudo apt install -y podman nodejs   # or: dnf install podman nodejs

Docker (docker.io) and containerd's nerdctl are detected too — whichever you already run is fine.

Windows

Install Docker Desktop (or podman) and Node, then fetch the runner from PowerShell:

winget install Docker.DockerDesktop OpenJS.NodeJS
iwr -useb https://deepresearch.se/cure/local-exec/runner.mjs -OutFile runner.mjs; node runner.mjs

Running inside WSL works the same way and is usually faster — install podman or docker in the distro and use the Linux line.

No Node? Run the runner itself in a container

One command, nothing installed on the host but Docker. The runner runs inside a container and drives the host's Docker to create the throwaway machines:

docker run --rm -p 8100:8100 -v /var/run/docker.sock:/var/run/docker.sock node:22-alpine sh -c "apk add --no-cache docker-cli curl && curl -fsSL https://deepresearch.se/cure/local-exec/runner.mjs -o /tmp/runner.mjs && HOST=0.0.0.0 node /tmp/runner.mjs"
Read this one before you paste it. Mounting the Docker socket gives that container full control of Docker on your machine — which is exactly how it creates the sandboxes, and also why it is not a security boundary against the container itself. Convenient on a development machine; not something to run on a server you care about.

Podman's socket works the same way (-v /run/user/$UID/podman/podman.sock:/var/run/docker.sock).

Choose the machine your commands get

Any image with /bin/sh works. Point the runner at the toolchain your research actually needs:

IMAGE=python:3.12-slim node runner.mjs

By default the container has no network — it cannot reach the internet, your LAN, or the runner. Open it when you want the agent to be able to install packages, and know what you are opening:

NETWORK=bridge IMAGE=python:3.12-slim node runner.mjs

To let the agent see a project directory, mount it — it appears as /mnt inside the container:

MOUNT=~/code/my-project node runner.mjs

Everything the container writes outside a mount disappears with it. A session's machine is kept warm across the whole research turn, so cd, installed packages and written files survive between commands, then it is destroyed.

Options

All configuration is environment variables:

VariableDefaultWhat it does
PORT8100Listen port.
HOST127.0.0.1Bind address — localhost only unless you widen it.
BACKENDautocontainer, docker, podman, nerdctl — or host for no container at all.
IMAGEdebian:stable-slimAny image with /bin/sh.
NETWORKnonenone, bridge or host.
API_KEYnoneWhen set, commands must carry it (x-api-key). Paste the same key into the settings drawer.
MOUNTnoneHost directory to mount at /mnt.
MEMORY / CPUS / PIDS2g / 2 / 512Per-container limits.
IDLE_MINUTES30Destroy a session's machine after this much silence.
ALLOW_ORIGIN*CORS origin; tighten to https://deepresearch.se if you like.

Check it's alive

curl -s http://localhost:8100/healthz
curl -s -X POST http://localhost:8100/exec -H 'content-type: application/json' -d '{"command":"uname -a"}'

Bring your own runner

The script above is a reference implementation, not the interface. The interface is DREE/1, two endpoints:

EndpointShape
GET /healthz{ok, protocol:"dree/1", backend, image, ephemeral, network}
POST /exec{command, session?, timeoutMs?, maxStdoutBytes?} → {exitCode, stdout, stderr, truncated?}

Anything answering those drops straight in: a Firecracker or Cloud Hypervisor pool, a gVisor sandbox, a remote build box over a tunnel, your company's CI runner. session is the only subtlety — commands sharing a session id should reach the same machine, so a research loop keeps its working directory between rounds.

Good to know

  • Browsers. Chrome, Edge and Firefox allow an HTTPS page to call http://localhost, and the runner answers Chrome's private-network preflight. Safari blocks it as mixed content — use another browser, or put the runner behind a local HTTPS proxy.
  • Fail-soft. If the runner is down or unreachable, research falls back to answering without a shell; you get an answer either way, and the status line in Settings tells you which environment actually ran.
  • It is a sandbox, not a vault. A container limits what a mistaken (or misled) command can reach; it is not a guarantee against a determined escape. Keep NETWORK=none unless you need otherwise, mount only the directory you meant to, and do not point it at a machine holding things you cannot lose.
  • Watch it work. Every command the assistant runs is printed in the runner's console, with its exit code and how long it took.
  • Keep it local. The runner binds 127.0.0.1 and writes nothing to disk. If you expose it beyond localhost, set API_KEY and tighten ALLOW_ORIGIN.
  • The browser VM is still there. Switching back is one dropdown; nothing about your research or history changes with it.
