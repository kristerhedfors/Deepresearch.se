DeepResearch.Se/rver documentation

← Back to the app

This page documents the signed-in tier, DeepResearch.Se/rver: hosted deep research with live web search, accounts, and cloud storage. If you are using the khaki, no-account tier that runs entirely in your browser, read the DeepResearch.Se/cure documentation instead. Its storage and privacy story is deliberately different: everything stays in the browser.

First, what this project is for

DeepResearch.se is innovation and research into the privacy capabilities of LLM applications. The question it exists to answer: how far can a real, useful research assistant be pushed toward provable privacy — privacy you can check rather than take on trust — and where does that start costing capability? The proof is not a white paper. It is this site, open-sourced whole, so every claim below is one you can verify yourself. It is genuinely experimental and nowhere near production-ready; treat it as a working research instrument.

What it brings you

  • Deep research that shows its work — searches planned, run and cited, on a time budget you set, with the reasoning steps visible as they happen instead of a spinner and a wall of text.
  • Two tiers, so privacy is a choice you make rather than a promise you accept — one where the server is never in the data path at all, one where it is and earns its place with capability.
  • Research that travels — a workspace can be handed to someone as a single link, with a bounded, revocable allowance inside it, and their findings can come back sealed.
  • A real Linux machine in the browser tab — the assistant runs code and reads actual output, and the execution never leaves your device on either tier.
  • Models on your terms — EU-hosted by default, US providers if you choose them, your own local server, or a model running on your own device with no prompt leaving it at all.
  • More than one kind of agent — a research agent, one that answers from this site's own source, one that builds and publishes small apps, one that plans a team of sub-agents, one that reads the outward feed of what everyone else shipped.
  • It is also a tool for your agents — the same pipeline is an MCP endpoint, so Claude, Cursor or anything else that speaks MCP can call it.

See something you like? Take it

Adaptability is a primary design goal. The point of open-sourcing this is that you fork the architecture and run it for your domain and your requirements — ideally into an environment already network- and authentication-restricted, so the whole serving chain is yours. What makes that realistic:

  • Zero runtime dependencies. package.json has no dependencies block at all; the Worker imports nothing but node: builtins and its own files. No build step, no bundler, so there is no transitive tree to audit and nothing to break between you and a deploy. The browser libraries that are needed are vendored and served from our own origin — a first visit costs 69.7 KiB, everything heavier is gated behind a feature you reach for.
  • Frequent refactoring for modularity, as standing practice — ten recorded passes so far. Every large feature is a pure, testable core plus thin orchestration, which is what makes a piece liftable: take the crypto core, the pipeline, the sandbox or the retrieval layer without taking the rest.
  • Third-party services are extensions, never core. Adding or removing an integration is one descriptor in a registry and touches no core file — enforced by a test that fails the build if a core module so much as names a service.
  • Swap the platform underneath. Every Cloudflare binding is documented with what it is used for and what substitutes for it — static assets, SQLite, an S3-compatible store, any vector database. The README's install walkthrough and its "running outside Cloudflare" section are the map.
  • Deterministic by design, so it runs on the models you have. Every planning phase is a plain JSON call — no function calling anywhere in the pipeline — so the whole thing works on models with unreliable tool support, including small ones you host yourself.
  • Distil it instead of reading it. Two SDKs ship with the project: 34 modules for building a platform like this one, and an agent specification for building agents on it. Agent Studio, in the app, turns a description into either a new agent or a whole new platform and publishes it live.
  • Open interchange standards. The workspace bundle (DRSW/1) and the pipeline structure (DRPL/1) are written as specifications, with this site as their reference implementation — so a workspace or a pipeline you build is not locked to this codebase. Both names open the standard itself: wire format, payload sections, conformance classes, versioning, written for an implementer who has never seen this repository. They are drafts that run ahead of the code on purpose, and DRSW/1 §6 records which conformance class this site actually meets. A third wire, DREE/1, does the same for where the agent's shell commands run — two endpoints a machine of your own answers on, in place of the browser VM. The argument for writing any of it down is stackless research.
  • MIT-licensed, and checkable end to end. The live site is served straight from the public repository, git-connected, so what production runs is what you can read.

The design in full is the architecture story; the complete dependency inventory, the privacy model and every other design document are at /docs/. What follows here is the practical manual for the signed-in app.

Start here: what this site is

It is a research assistant that works from sources, not from memory. You ask a question in plain language — English or Swedish — and instead of answering off the top of its head, the site plans a handful of web searches, runs them, reads what comes back, and writes you an answer with numbered citations you can click. You choose how long it is allowed to spend, from 15 seconds to 10 minutes, and that budget decides how thorough it gets: a quick cited brief at one end, a full research report with sections and tables at the other.

Your first question, end to end. Nothing here needs setting up first; the defaults are the intended way to use the site.

  1. Type the question in the pane at the bottom and press the arrow. (Enter makes a line break — the arrow is the only way to send.)
  2. Watch it work: it tells you what it is searching for and which sources it found as it goes, rather than leaving you at a spinner.
  3. Read the answer. Citations are numbered and linked; Raw, Copy and PDF sit underneath it.
  4. Ask a follow-up. The conversation is kept, so it builds on what came before, and it is saved automatically for you to reopen later.

Two controls in that pane are worth knowing from the start: the time slider (how long it may spend) and the spiderweb knob (web search on or off). Both are covered under the input area.

What it is running on. The default AI models run at Berget.ai (🇸🇪 EU-hosted). If an administrator has enabled them, you can also choose 🇺🇸 Claude or GPT models, which process your conversation at Anthropic or OpenAI in the US. Your conversation goes wherever the model you pick resides; the model selector flags each choice with its provider's country so you can tell at a glance. Web searches go through Exa.

Privacy in one line: what matters is where your data goes. Your conversation is processed wherever the model you pick lives — Berget in the EU (🇸🇪) by default, Anthropic or OpenAI in the US (🇺🇸) if you choose one of theirs — and your history rests in this site's storage, held by whoever operates this site. The server also logs completed exchanges to improve the service. Encryption is applied throughout as ordinary good practice; residency is the part that decides who can read what. For chats that should leave no trace on this server at all, the ghost button (upper right) opens ghost mode: DeepResearch.Se/cure, the client-side twin of this app where the server is never in the data path (your own API key, browser-local storage). Privacy, in full is the complete account.

Beyond a single question

Cited research is what you get without touching a setting. Everything here is optional, and each has its own section further down this page or its own page:

  • Workspaces (the app still labels them projects) — a named place holding chats, files and notes, with retrieval across all of it, so a body of work accumulates instead of scattering across conversations. See chat history and which workspace.
  • Attachments — images and documents, read in your browser, and flagged before you send if they carry hidden metadata. See the input area.
  • Other assistants than Deep Research — the chat-mode dropdown swaps in Introspection (answers from this site's own source code), Agent Studio (turns a description into a small published app), Orchestrator (plans a team of sub-agents and runs them), and Outrospection (answers from the outward feed of what everyone else shipped). They are bundled examples of what this platform carries, not separate products. See the input area.
  • Quizzes — ask to be quizzed on anything and the answer becomes an interactive quiz. See quizzes.
  • A Linux machine in the tab — the experimental execution sandbox boots real Debian inside the browser so the assistant can run code and use the actual output. Off by default; see settings.
  • The pipeline as a tool for other agents — the same research endpoint is exposed over MCP, so Claude, Cursor or any MCP client can call it. POST /mcp, documented in the repository.

Which workspace: Se/cure or Se/rver?

This site ships the same assistant twice, and picking between the two is the most consequential choice you make here. One question decides it: would it be a problem if the operator of this site could read this? If yes, use a Se/cure workspace — the whole thing rides a single link, stays in your browser, and no server record of it exists anywhere. If no, use a Se/rver workspace, the signed-in kind this page documents, and get live web search, maps, retrieval at scale and sync across devices in exchange.

The honest trade in one line each: Se/cure costs capability — no hosted search, no maps, no sync, and no recovery if you lose the password. Se/rver costs exposure — your work sits in a cloud account, indexed material rests readable, and completed exchanges are kept in the site's research log unless you use ghost mode.

The full comparison lives in one place, so it stays consistent: the architecture story pairs the two tiers row by row — privacy, capabilities, and what a workspace is, where it rests, who can read it, and what happens when you hand it on. Read that if you are deciding. The Se/cure documentation carries the same chooser written for the no-account side, and docs/WORKSPACES.md §2 is the complete written specification, readable in-app at /docs/.

Chat history — where it lives

Every conversation you have is saved automatically, right here in your browser, so you can pick it back up later. The History panel (list icon in the header) lists them by their first question, most recent first. Click one to reopen it (this also restores the model, time target, and web-search setting it was sent with); the pencil renames it, the trash bin deletes it.

Where it actually lives: in this browser's IndexedDB (the modern, larger-capacity successor to localStorage), and, always, an encrypted copy in this site's storage as well, so your history follows your account across devices. There is no switch: on this signed-in tier, cloud storage simply is how history works. The server never holds a readable copy of your saved history; the cloud copy is ciphertext. Separate from history, completed exchanges go to the server's interaction log unless the conversation was started incognito (see "Privacy, in full" below).

If you want conversations that are stored in the browser only, with no server copy even possible, because the server is never in the data path at all, that is the client-side tier, DeepResearch.Se/cure: see its documentation.

Encryption, briefly

Conversations are encrypted (AES-256-GCM) before they touch storage, in this browser and in the cloud copy alike. The key is derived per account on the server, fetched fresh each page load and held in memory only — never written to localStorage, IndexedDB, or any other disk-backed storage — so a browser examined at rest yields ciphertext without the key beside it.

That is worth having, and it is also the limit of what it buys you here. The server holds the ciphertext and the secret your key is derived from, so a compromised live server could decrypt your history, and some material is stored readable on purpose because retrieval needs plain text (see "The exception" below). Encryption protects storage at rest — a stolen device, a leaked bucket. It cannot mean the operator of this site is unable to read your work. The tier you are on is what decides that. If a conversation must not be readable by anyone running a server, it belongs on DeepResearch.Se/cure (its documentation), where the server sees neither ciphertext nor key because it is never in the data path at all.

What this means day to day

  • History follows your account. Sign in on your phone and your conversations are there too, pulled down as encrypted records and decrypted locally. Clearing one browser's site data loses nothing; the cloud copy restores it.
  • Conversations that must stay out of any cloud don't belong on this tier at all. Use DeepResearch.Se/cure (the ghost button), where everything rests in your browser only and the server is never in the data path.
  • If this server hasn't configured cloud storage, the app runs browser-only: conversations still save locally, they just don't follow the account.

The exception: chats inside a project

A project here is a workspace — a named place holding your chats, files and notes. That is the word the documentation now uses for both tiers: a Se/rver workspace is this one, stored in your account; a Se/cure workspace is the same idea sealed into a single shareable link, with no server record at all. The buttons in this app still say "project" until they are relabelled.

A chat that belongs to a project is indexed for retrieval, the same way project documents and notes are, so your other chats in that project can automatically draw on what was worked out in it. The index keeps growing as the conversation does: each new exchange is added to it. Because a search index needs readable text, indexed material is stored readable, not encrypted, and that includes project chats themselves, in this browser and in the cloud copy. Chats outside projects are not indexed and stay encrypted exactly as described above. If a conversation shouldn't be readable at rest, or retrievable from your other chats, keep it outside projects, or take it to ghost mode (the ghost button → DeepResearch.Se/cure, where nothing reaches this server at all).

Backing up or moving a project with a secret

A project, even one kept out of the cloud, can be stored as one encrypted archive keyed by a secret: open the project and press Store next to "Encrypted copy, keyed by a secret". Your browser packs the project's chats, files, and search index, encrypts everything locally with a freshly generated secret (DR1-XXXX-…, 160 random bits), and uploads only the unreadable result. Unlike regular cloud storage, the server never holds anything readable: not the project's name, not its files, not even a key it could derive. The secret shown to you (once, so copy it!) is the only way to find and decrypt the copy. Use 🔑 Load project from secret in the History panel on any of your devices to bring the project back. Storing again replaces the copy under a new secret, and the old secret stops working; losing the secret loses the copy, with deliberately no recovery.

The input area

  • Text field — type your question. Enter inserts a line break; nothing is sent until you tap the arrow. The field grows up to about six lines.
  • Paperclip — attach images or documents (pdf, docx, md, txt). Each attachment appears as a small card above the bottom edge of the pane, with a white ✕ to remove it. Documents are read in your browser; their extracted text travels inside your message. The files themselves are never uploaded anywhere. Images need a vision-capable model (you'll be offered a switch) and are downscaled in your browser first.
  • Camera — take a photo with your device's camera and attach it, same rules as an attached image.
  • Model selector (next to the send arrow) — picks which AI model answers, flagged with its provider's country (🇸🇪 EU-hosted Berget models by default; 🇺🇸 Claude or GPT models if enabled here). Models that are down for maintenance show as greyed out and come back automatically. Your choice is remembered in this browser.
  • Chat mode (the dropdown beside the model selector) — picks which assistant answers, and repaints the app in that mode's colour. Deep Research (blue) is the ordinary research pipeline described on this page. Introspection (titanium) answers from this site's own source code instead of the web. Agent Studio (green) turns a description into a small published app of your own. Orchestrator (violet) plans a team of sub-agents and runs them in the background, drawing the workflow as it goes. Outrospection (newsprint) is Introspection's mirror image: instead of this site's own source it answers from the outward feed of what everyone else shipped, and only from articles that feed actually holds — you can read the same feed at Outrospection. The last four are bundled examples of what this platform can carry rather than separate products; switching back to Deep Research at any time restores the normal behaviour, and your pick is remembered in this browser.
  • Attachments can carry more than their visible content. Photos often embed where and when they were taken and what device took them; Word documents can carry the author's name, edit history, and reviewer comments, sometimes including text that was deleted but is still physically present in the file. Since this is often exactly what a research question is about ("where was this photo taken", "what did this document originally say"), it's extracted along with the visible content and sent as part of your message. Whenever anything is found, the attachment's card shows a small badge before you send: a plain "ℹ️ metadata included" for routine details, or a distinct "📍 location data included" (a photo's GPS coordinates) / "⚠️ tracked changes included" (a document's unaccepted deletions) for the two cases worth a second look. Remove the attachment if you'd rather not include what the badge is telling you about. A photo's raw coordinates are also resolved server-side into an actual place name (via OpenStreetMap Nominatim, where only the coordinates are sent, nothing else) since a place name is far more useful for research than bare numbers.
  • Spiderweb knob — the web-search switch, with a spiderweb inside the knob: it glows blue when search is on and turns grey when off. Tap to toggle; press and hold it for a short explanation of the switch. This is the control with the biggest privacy meaning; see the next section.
  • Slider + time — your research time target, from 15 seconds to 10 minutes. More time buys more search angles, more follow-up rounds, and a fact-checking pass, plus a more thorough answer: the bottom of the slider delivers a quick cited brief, the default a focused answer, the middle a structured report with sections, and the top a full research report (executive summary, thematic sections, tables, limitations). The readout right of the slider shows the time and what it delivers. The slider stays active regardless of the web-search knob: depth is how deep the assistant goes over whatever sources are available, so it still shapes the answer with web search off (see the next section).
  • Arrow — sends the question. This is the only way to send.

On each answer

  • Raw — toggles between rendered and plain-text view.
  • Copy — copies the answer text to your clipboard.
  • PDF — downloads the answer as a formatted report tagged DeepResearch.se, generated entirely in your browser.

Quizzes — test yourself on anything

Ask to be quizzed ("quiz me on this document", "quiz me on the French Revolution with 8 questions", "förhör mig på kapitlet") and the answer becomes an interactive quiz: one question at a time, each with multiple-choice alternatives plus a free-text field to answer in your own words, immediate feedback with a short explanation after every answer, and a final score with a per-question recap at the end.

  • The material is up to you — the conversation so far, an attached document, your project's files and notes, or (with web search on) fresh web research on the topic you name.
  • Written answers are graded on meaning, not exact wording: synonyms, paraphrases, and another language all count. If a written answer can't be graded, it's shown as ungraded and simply doesn't count toward the score.
  • The result stays in the conversation — after finishing you can ask follow-ups like "explain the ones I got wrong", and a reopened conversation shows the finished quiz (or lets you resume an unfinished one).

Web search on / off — and what it means for privacy

On (knob blue): the AI plans a few search queries derived from your question, runs them against Exa, and answers from the sources it finds, with citations.

Off (spiderweb grey): no query is sent to Exa. The knob gates web search only: the time slider stays active, because depth is how deep the assistant goes over whatever sources are available. With Exa off it still researches within your time target using the other sources that apply (the Hugging Face Hub for a model/dataset question, or this site's own source in developer mode), and otherwise answers from the model's own training knowledge, in both cases with the depth the slider buys. Only when no such source applies are no web requests made at all.

Privacy: with web search ON, short search queries derived from your question are sent to Exa (never your full conversation), and Exa retains those queries by default (see the next section). With web search OFF, nothing is sent to Exa; any other source the assistant uses receives only a short derived query (a Hugging Face Hub lookup, say, never your conversation), and if none applies, nothing leaves except the conversation itself going to your chosen model's provider (Berget in the EU, or Anthropic/OpenAI in the US) to generate the answer. Either way, our server stores no message content.

Sensitive topics — a two-step, semi-private workflow

Be aware: Exa is not a zero-data-retention service by default. The search queries it receives may be retained under Exa's own policies. Exa offers true zero data retention only as a paid enterprise arrangement, which this site does not currently have. The queries are short and AI-derived, never your full conversation, but on a sensitive subject even a short query reveals the topic.

You can also change who does the searching. Press and hold (or hover) the web-search knob: the card that opens carries a source picker. Pick this site's Worker and searches run from our own Cloudflare Worker instead — it reads a public results page and the result pages directly, so no search company receives the query at all. The tradeoff is ranking: a public results page is weaker than Exa's research index, and the pages it reads still see a request from us. The pick is stored on this device and applies from the next question onward.

If that matters for your question, split the work in two:

  1. Fetch generically. With web search on, ask a broad, impersonal question about the subject, the kind that could appear in any textbook index ("current treatment options for X", "how does Swedish law regulate Y"). The assistant searches Exa and pulls the source material into the conversation. Keep names, case details, and anything personal out of this step: it is what Exa sees.
  2. Ask specifically. Turn web search off and ask your real questions. Nothing further is sent to Exa; the model answers from the sources already fetched into the conversation (plus its own knowledge). The other sources are topic-gated (a Hugging Face Hub lookup only fires on a model/dataset question), so an ordinary sensitive question sends nothing further out.

If the step-2 answer lacks source material, flip search back on for another generic round on the missing angle, then switch it off again and continue.

This is semi-private, not anonymous: your generic step-1 queries were still seen (and possibly retained) by Exa, and the whole conversation, including the fetched excerpts, is still processed by your chosen model's provider (Berget in the EU, or Anthropic/OpenAI in the US) on every turn. For anything truly sensitive, keep identifying details out of the chat entirely.

Settings

Account & usage → Settings holds the on/off switches for your account. Each is a single line; press and hold (or click) the ⓘ next to a switch for the full explanation.

  • History is stored in the cloud (always on, an informational row, not a switch) — your conversations, files and search index are kept in this site's storage so your history follows your account across devices; that is what this signed-in tier is for, and the opposite of Se/cure, which never stores anything server-side. Conversations and files are stored encrypted; indexed material (large documents, project files and notes, project chats, and the search index itself) is stored readable, since retrieval needs readable text. See "Chat history" above for how the encryption works.
  • Shodan host intelligence (off by default) — when on, if a question mentions an IP address or hostname, the site looks it up on Shodan and folds what it finds (open ports, running services, the hosting organization and ASN, location, and any known CVEs) into the research so the answer can use and cite it. Only the IP or hostname itself is ever sent to Shodan, never your question or anything about your account, and only when your message actually names a host. It works whether or not web search is on.
  • Google Maps & Street View (off by default) — when on, if a question names a street address (or you attach a photo carrying GPS location), the site looks it up on Google Maps Platform: it resolves the place with the Places API (name, address, type, rating), confirms Google Street View coverage and its imagery capture date, and pulls a road map, then folds those details and clickable Maps/Street View links into the research, and hands the Street View (several angles around the spot) and map images to a vision-capable model to describe. When Street View coverage exists you also get an inline, drag-to-navigate Street View right in the answer. Only the address itself (or a photo's coordinates) is ever sent to Google, never your whole question or anything about your account, and only when your message actually names an address. It works whether or not web search is on.
  • Feedback (no switch) — feedback is given straight from the chat: start a message with the word “feedback” (for example “feedback: the map view was cut off”) and, instead of researching it, the site passes your note to its developers and confirms it was sent. Their replies come back as a short thread under Feedback in the account panel. Only the message you send that way is shared.
  • Execution sandbox (off by default, experimental) — when on, for questions that call for running code, a small Linux environment boots inside this browser tab and the assistant can run shell commands in it, folding the real output into its answer. It runs entirely on your device; nothing about the commands or their output leaves the browser. Being experimental, it may be rough or slow to start.
  • Developer mode (off by default) — when on, the assistant can answer questions about how this site itself is built, drawing on its own source code, instead of declining. Handy if you're curious about the implementation.

Privacy, in full

  • Conversations: processed by your chosen model's provider to generate answers: Berget in the EU (🇸🇪, the default), or, if you pick a Claude or GPT model, Anthropic or OpenAI in the US (🇺🇸). The model selector flags each model's country. Saved locally in your browser and, always, as a cloud copy in this site's storage — the tier is the choice, there is no switch (see "Chat history" above). Both copies are encrypted, and both are erased when you delete a conversation. Chats inside a project are the exception: they're indexed for retrieval and stored readable, like the project's documents (see "The exception" above).
  • The interaction log: to improve the service, the server logs each completed exchange: your question, the answer, the searches run and sources found, timings, and any error. For conversations that should never touch this server, the ghost button takes you to ghost mode: DeepResearch.Se/cure, where the server never receives your messages in the first place. (API clients can still send incognito: true per conversation to suppress the log row.)
  • Project vault copies: made only when you press Store on a project's "Encrypted copy, keyed by a secret". The archive is encrypted in your browser under a secret only you hold; the server stores unreadable bytes it has no key for, not even derivable. Load one back with 🔑 Load project from secret in the History panel.
  • Search queries: sent to Exa only while web search is ON, and only as short queries the AI derives from your question. Exa retains queries by default (zero data retention is an enterprise-only Exa feature we don't currently have); see "Sensitive topics" above for the two-step workflow.
  • Shodan lookups: only if you turn on Shodan host intelligence in Settings (off by default). Then, when a message names an IP or hostname, that IP/hostname alone is sent to Shodan to fetch its public infrastructure record, never your question or anything identifying you.
  • Google Maps lookups: only if you turn on Google Maps & Street View in Settings (off by default). Then, when a message names a street address (or you attach a located photo), that address alone (or the photo's coordinates) is sent to Google Maps Platform to fetch the place, its Street View coverage and a road map, never your whole question or anything identifying you.
  • What our server keeps: your account (Google email, name), per-request usage numbers (token counts, search counts, durations) used for the quota bars, the interaction log above, the encrypted history copies, and the readable indexed material described under Settings (chats in ghost mode, Se/cure, never reach the server to begin with).
  • Cookies: dr_session (keeps you signed in) and dr_privacy_ack (remembers you saw the privacy notice).
  • In your browser only: model choice, time target, and the web-search switch position (localStorage). If you switch away mid-research, a small marker (the conversation and request ids plus those same settings, never any message text) is also kept there briefly so the app can pick the finished answer back up when you return, even if the phone closed it in the background; it clears itself once the answer arrives, and expires within 15 minutes.
  • Sign-in: Google only. We receive your verified email and name from Google; we never see your Google password.
