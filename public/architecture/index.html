One product, two answers to the same question

DeepResearch.se is a research project on the privacy capabilities of LLM applications, and this pair is the proof. It ships the same deep-research assistant twice. DeepResearch.Se/cure is the public client-side tier, where your browser is the research engine and the server stays absent from every data path. DeepResearch.Se/rver is the signed-in tier, where a Cloudflare Worker orchestrates the research. Both share the floating glass UI (Se/cure in khaki), the five-phase pipeline shape, and the no-function-calling determinism. They give opposite answers to one question: "where is the user's data allowed to exist?".

The trade this page visualizes, in short: Se/cure buys privacy structurally. The server cannot log, leak, or be compelled to reveal what never reaches it, and it pays for that with the capabilities only a server can hold keys for. Se/rver buys capability by having a server: live web search, maps, host intelligence, attachments, accounts. It protects the data that server handles with encryption and policy.

The two data paths

First-class claim: this code arrives via Cloudflare, straight from GitHub

First, the serving chain, because every structural guarantee on this page begins only after the code reaches your browser. The live site, DeepResearch.Se/cure included, is deployed on Cloudflare and served directly from the public GitHub repository: git-connected, so a push to main is exactly what production serves. That is what makes the no-server-data-path claim independently verifiable, because the code your browser runs is the code anyone can read. It is also the trust boundary: trusting the live site means trusting that serving chain (the repository and the Cloudflare account that deploys it).

So to make it really secure: build upon it. That is the point of this project. The architecture is meant for anyone to take and deploy for their own use case, ideally into an environment that is already network- and authentication-restricted, so the serving chain is theirs end to end. In return it gives you an easily extendable platform with some peculiar features: a research pipeline that runs client-side, sealed browser-local state under a user-held secret, lendable capability grants, and a Linux VM that boots in the tab. Those features are the subject of this research and innovation project.

Fork it: github.com/kristerhedfors/Deepresearch.se. The README's "Installing your own instance" walks through a complete deployment.

Privacy, paired

The same concerns, answered by each architecture. The pattern to notice: on DeepResearch.Se/cure each row is a consequence of the structure. There is no server-side behavior to trust, because there is no server-side behavior. On DeepResearch.Se/rver each row is a promise the code keeps.

DeepResearch.Se/cure DeepResearch.Se/rver
Identity No accounts at all. Nothing to sign in to; nothing to attribute a question to. Google sign-in, invite-only approval, quotas per account.
Conversations at rest One sealed archive in the browser's own storage: chats, the RAG index (chunk text and vectors), and your provider API keys, AES-256-GCM under a secret only you hold. Stricter than Se/rver's RAG exception: even indexed material rests as ciphertext. Ciphertext in the browser (IndexedDB, AES-GCM) and, always and with no knob, the same ciphertext in R2. Readable exceptions, because retrieval needs plaintext: RAG-indexed material and project chats. The encryption key is derived server-side, held only in memory, never at rest beside the ciphertext.
Interaction log Structurally impossible. The question and answer travel browser → provider on your key; the server never carries either, so there is nothing it could log. A full-visibility chat log (complete question, answer, research metadata) in D1, an explicit product decision (2026-07-08) that powers the agentic debugging and feedback loops. Suppressed for any request carrying the incognito flag, so the API promise the ghost feature made stays honored.
API keys Your own keys, pasted once, living inside the sealed state in your browser. Each key is sent only to its own provider, straight from the browser. Server-side secrets (Berget, Anthropic, OpenAI, Hugging Face, Exa, Maps, Shodan). Users never handle a key; keys never appear in any log.
What third parties see The provider you chose sees your questions (that's inherent to using any model API), under your account and data-processing terms with them, not ours. The minimum for the job: a search query, a coordinate, a hostname. Never the conversation, a filename, or the account identity.
The strictest tier The whole tier is that property. The vault's crypto core (vault-core.js) is the foundation Se/cure's sealed state is built on. The secret-keyed project vault: a whole project archived server-side as ciphertext under a user-held secret the server never sees and cannot derive. One feature with the structural property.
In one line Privacy by structure. No promise needed. Privacy by encryption and policy. Auditable promises.

Capabilities, paired

What each side of the trade buys. Rows where Se/cure matches Se/rver are the deliberate ports. Rows where it can't are the capabilities that require server-held keys or a server-side data path.

DeepResearch.Se/cure DeepResearch.Se/rver
Research pipeline The same five-phase shape, ported to the browser, with the search wave replaced by an offline knowledge harvest. Same determinism and fail-soft invariants, verified end to end in tests. Triage → search → gap check → synthesis → validation, orchestrated by the Worker. Deterministic, no function calling, every helper phase fail-soft.
Sources No web search (no server to hold the Exa key). The harvest phase pools the model's own knowledge, and the prompts force honesty about that limit. Live Exa web search waves with a numbered, domain-diverse source registry; Hugging Face Hub joins as citable sources when asked.
Models CORS-capable providers only, because the browser must be able to call them directly: OpenAI, Anthropic, Hugging Face, Groq and Berget as named shortcuts, plus any other OpenAI-compatible endpoint you point it at — a hosted service or a model server on your own machine. Hugging Face is the open one: its router fronts a marketplace, so the model list fills from the live catalog rather than a handful picked for you. Split routing survives: JSON phases run on each provider's fixed cheap JSON model. The full Berget catalog, key-gated Claude and GPT answer models, and any Hugging Face model this account enabled — the open catalog is browsed, priced and turned on in the Models agent, then appears in every agent's dropdown. JSON planning phases always on the fixed reliable model (split routing).
Documents & RAG Project & chat RAG, browser-direct embeddings on your key (OpenAI small/512-dim by design; Berget too; a session on a provider that serves no embeddings — Anthropic, Groq, Hugging Face, or most custom endpoints — simply runs without RAG, fail-soft). Attachments (pdf/docx/images with metadata extraction), project files, chat RAG, with embeddings via the Worker's /api/embed proxy.
Enrichments None. These are the capabilities that exist only because a server holds the keys and takes the minimal-disclosure role. Google Maps / Street View scenes, Shodan host intelligence, reverse geocoding, the image deck. All opt-in knobs, all server-keyed.
Accounts & continuity Browser-local projects with save-as-project and /my/project-<hash> deep links; published research replays open in place and continue on your own keys. No accounts to sync. Quotas, usage windows, cloud sync (knob-gated, ciphertext), cross-device projects, the message center, the feedback pipeline, quizzes, games.
Execution sandbox Shared, and identical. The same x86 Linux VM boots in the browser tab on both tiers (next section). The only difference is who picks the next command: on DeepResearch.Se/cure even that decision happens client-side on your key; on DeepResearch.Se/rver the Worker's reliable model does (/api/bash/step). Execution never leaves the browser on either tier.

Workspaces: the unit that travels

Underneath the pair, this project is a security architecture for distributed deep research: how work goes out to people and machines you do not control, and how insight comes back, with the exposure of every hop written down instead of assumed. The thing that travels is a workspace — a named place holding material, conversations, configuration, and capabilities. Everything else on this page is machinery a workspace uses.

Se/cure workspace Se/rver workspace
What it is One link. The whole workspace — settings, chats, optionally your keys and borrowed allowances — rides the URL fragment, which browsers never send to any server. An account-scoped place (the UI still labels it Project today): a record, its chats, its files and notes, and a vector index over them.
Where it rests In the link, and in your browser under a secret only you hold. There is no server-side record to seize, log, or leak. Encrypted in the browser and in R2. Indexed material and the workspace's own chats rest readable, because retrieval over ciphertext retrieves nothing.
Who can read it Whoever holds the link and the password — which travel by different channels, and are worth 8192 hash rounds per guess to an attacker. You, and the operator of one Cloudflare account. That is the honest cost, and the smallness of it is the point: one provider, one Worker, one deterministic pipeline.
What it can do The full client-side pipeline on your own or local model, the Linux sandbox, browser-side retrieval — plus any capability the sender chose to lend, bounded and metered. All of that, plus live web search, maps and host intelligence, retrieval at scale, sub-agent orchestration, and the pipeline as an MCP tool.
Handing it on Send the link. Nothing is registered anywhere. What the sender can still withdraw is every borrowed capability inside it — set a quota to zero and the link keeps opening but stops spending. Invite by workspace link or campaign, or lend your own machine's model as pooled compute. Findings come back as sealed conclusions you import.

The return path is where the trade gets sharpest. Contributors mark an answer with 👍 to include it — the question, the answer, and the tool results behind it — and 👎 to forget one, which drops it from what is sent and from the context of everything else. A sealed conclusion sent to the site's inbox can be decrypted when the workspace admin imports it; a conclusion sealed to a campaign organizer's own key cannot be read by the site at all. Which of those you are in gets said plainly, in a popover, before you contribute anything.

The tables above are the comparison — this page is where it lives, so there is one copy to keep true. Written for the person deciding rather than the person implementing, point by point (what you need to start, who can read it, who pays, what you give up either way), it is the chooser in the Se/cure documentation; the Se/rver documentation is the overview of the signed-in app and points back here. The full written specification of both kinds is docs/WORKSPACES.md in the repository.

The shared engine room: a real Linux inside the browser tab

The experimental execution sandbox (the bash-lite agent, default off) is the clearest expression of the whole architecture: even on the server tier, the server never runs a shell. A CheerpX x86 emulator, compiled to WebAssembly, boots a stock Debian Linux entirely inside the page. The agentic loop feeds it commands through a fenced-block convention (no function calling, like everything else here), and the resulting transcript feeds synthesis as ground truth.

Which Linux, exactly — and why "big" is fine

The disk is the public WebVM image debian_large_20230522, a stock Debian, about 4.7 GiB of ext2, streamed over WebSocket from disks.webvm.io. That sounds like the wrong image for a browser until you see how it's read (a deliberate keep-as-is decision, reviewed 2026-07-12):

  • Only touched blocks download. The disk streams lazily, block by block; a session that runs python3 and jq fetches those tools' blocks and nothing else.
  • Fetched blocks are cached in IndexedDB, so repeat sessions boot warm.
  • User data lives on separate volumes. The /workspace and per-project overlays are their own IndexedDB devices, so the big base image can be reset or re-streamed without touching your files.
  • The stock image is the capability. A full Debian means the agent finds real tools (python, coreutils, jq…) instead of a stripped busybox, and the transcript quality depends on that.
  • The expensive step is avoidable anyway: the host-command design means sessions that never need the VM never boot it at all.

Honest status: this is a borrowed stock image made economical by streaming and caching, not an image tuned for us. We keep it deliberately, because the boot-avoidance and lazy-block economics beat an image diet, and a smaller disk would cost preinstalled tools. The CheerpX runtime and the public disk service carry their own licensing terms to review before this graduates from experimental.

The pairing holds here too: the sandbox gives DeepResearch.Se/cure a capability that would otherwise be impossible (a no-server tier still gets code execution, because execution never needed the server in the first place), and it gives DeepResearch.Se/rver a capability without a privacy cost (your files mount into a VM that lives and dies in your tab, and the server only ever suggests the next command).

Why a pair, and not a setting

The two tiers share their UI, their pipeline shape, their crypto core (vault-core.js), and their sandbox, but they are separate architectures, not a toggle. A privacy property you can switch off is a policy; a privacy property the structure enforces is a guarantee. Keeping both tiers whole means every user gets to pick which trade they're making, and the ghost button in the main app is the door between them: it doesn't flip a flag anymore, it walks you to DeepResearch.Se/cure.
